Findings

  • Two different loading processes have fed this table over the years. The old one stopped running in 2020 (15,019,410 rows, frozen). The current one runs daily and touched data again this morning (6,958,825 rows)
  • Serious: the step meant to keep household level benefit flags correct only looks at households that still exist in the staging table frozen since 2020. Any household created or changed since then is silently skipped, its benefit flags never get re-evaluated
  • Serious, same root cause: the step meant to correct a card's points earning flag also only compares against that same frozen 2020 staging table. For any card active since then, there is no working mechanism left in this table's process to ever fix that flag once it goes wrong
  • Confirmed: the final step into this table inserts new cards and updates existing ones by matching the internal key. Every update also overwrites the basket discount and points earning flags with whatever the staging table has, which, as found above, is empty from the true source. This is not a hypothesis anymore, it is confirmed in code: any card touched by today's process loses these two settings
  • Confirmed: the step that copies data from the raw feed into the next staging table always marks every card as approved, and computes a fingerprint used to detect what changed. That fingerprint is built from name, address and contact fields only. A card whose only change is to its discount or points settings would not be picked up as changed at all
  • 26 other tables depend on this one, including the two largest transaction tables in the warehouse. This table has to be migrated before any of them

  • The process that injects placeholder members from the loyalty points source has not been identified.
    A confirmed placeholder process only handles a different source, the customer survey tool. A separate, still unidentified process must handle the loyalty points source.
  • What triggers the process that creates placeholder members from the customer survey tool has not been identified.
    That process has no schedule of its own and is not called by the main daily process, so something else triggers it. Not yet identified.
  • Whether a status column is populated only for one particular source system's rows, or the matching counts are a coincidence, has not been confirmed.
    Worth one more check before treating this as a real pattern.
  • How many cards already have their basket discount or points earning settings blanked out, versus still showing a real value, has not been measured.
    The cause is now confirmed: every card the daily process touches loses these two settings. A count would show how many cards are already affected.
  • The real, observed run schedule for this table's daily process, rather than what its schedule setting states, is still unknown.
    Earlier project notes claim it actually runs twice a day, not once as configured. Not reconfirmed this session.
  • The 15,183 stub member figure from references/anomaly-checklist.md has not been reconciled against this session's 240,954.
    This session's number is 16 times higher. Could be growth over time or a different counting basis. Left unresolved rather than asserted either way.

Important notes

A few things below are worth knowing before you rely on this table.

  • Important note on validation timing: Row counts for this dimension will not match Oracle during the wave that builds it (Wave 1). The Oracle table contains members inserted by POS_POINTS_EARN_F, migrating in Wave 3, that have not landed yet. This will look like a defect and is not one. Two checkpoints are needed instead of one: a structural checkpoint in Wave 1, confirming columns, keys and transformations, and a row count checkpoint after POS_POINTS_EARN_F lands in Wave 3. Filtering on APPRV_REC_IND separates real members from injected placeholders and makes the first checkpoint meaningful on its own.
