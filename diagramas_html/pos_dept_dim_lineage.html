Findings

  • The tables originally expected to feed this dimension are empty and unused. That did not mean the dimension itself is dead: a different process loads it directly from HQ's store department and accounting systems, with no intermediate staging step, and updates it daily, most recently today. This is the same pattern already found on the location dimension (LOC_DIM): same author, same scheduling style, same direct-load-from-HQ approach. Confirmed by directly checking: neither source table exists anywhere in this Oracle environment, under any schema or object type.
  • The live loading process's own internal activity logging is mislabeled under a different process's name, not its own. The identical mistake was already found on the location dimension's loader, which logged under yet another process's name. This looks like a repeated copy-paste habit across this author's direct-load files, not an isolated mistake.
  • 6 of the 101 department rows are unapproved placeholders, not real departments, and all have been frozen since 2014-2015, never touched again. The current live loader is not responsible for them: it always marks new rows as approved when its own source data is missing. Two utility processes exist that could in theory create this kind of placeholder, but neither can be tied to these specific 6 rows, and one of them is flagged as broken. Where these 6 rows actually came from is unconfirmed. This matters because one of them, department code '000', is behind 2,678,364 sales records, not a trivial edge case.
  • A second, undocumented table (PROD_POS_DEPT_DIM) exists with the exact same structure as this one. Its earliest record matches this table's earliest record down to a fraction of a second, strongly suggesting it is a copy taken at some point. It has not been touched since 2019, and nothing in the available material explains its purpose.
