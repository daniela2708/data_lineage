Findings

  • Two different processes could be updating this table today: one that has run daily since 2016 and matches a label found on every one of the table's 26 rows, and another built to run only once, back in 2013. Neither is confirmed as the one actually producing today's data
  • The data source the first candidate process is supposed to read from does not exist anywhere in the current database, and the process gives no indication of where it might actually live instead
  • A review of a different table's lineage turned up a note in the master orchestration file confirming this table's older update process was deliberately shut down in November 2015, not simply abandoned. The same file shows several other lookup tables were retired around the same time, all sharing this table's same unresolved current-loader pattern
  • The orchestration file for the second candidate process is internally mislabeled with a description belonging to a different table, a leftover from being copied from another setup rather than built specifically for this one
  • Additional files behind the second candidate process have since been reviewed. They confirm, and do not change, that this candidate only moves data through temporary staging tables and is not currently active
  • No new transaction types have needed to be added automatically since at least 2016; the safety-net processes that would otherwise create a placeholder entry for an unrecognized type have never had to run
