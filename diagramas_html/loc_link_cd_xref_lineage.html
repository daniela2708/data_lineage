Findings

  • The daily incremental update process contains a coding flaw: when a genuinely new record has no existing match, it is assigned a fixed placeholder value instead of a proper new key. If more than one truly new record appeared in the same run, they would incorrectly overwrite each other under that same placeholder value.
  • The full reload process resets the original creation date on every row each time it runs, overwriting the true history of when each record was first created.
  • The process that loads this table can be triggered from two separate schedules. Whether this causes the load to run twice has not been confirmed.
  • One of the five columns that make up this table's business key is missing a formal link to its reference table, unlike the other four. Whether this actually causes invalid values has not been measured, since checking it directly would require an expensive scan across two very large tables.
  • This table has a single confirmed source, marked 'HQ' throughout. It is live, with data as recent as 2026-09-03.
  • The full loading chain for this table is confirmed. Data arrives daily from the HQAnalytics system, is staged, matched against price level, price type, store and date reference data, and then either updated incrementally or fully reloaded.
