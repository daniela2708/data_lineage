Findings

  • Four versions of the staging step exist, and they behave differently: they include or exclude different kinds of records. One version's own internal naming suggests, but does not confirm, that it may write to a different staging table than the other three; that file is truncated before its actual write statement. Which version actually runs in production has not been confirmed, and getting this wrong would mean migrating the wrong logic.
  • About 1 percent of rows come from a second, unidentified source system, the same one that also feeds WAREHOUSE_SHIPT_F. These rows represent a different kind of delivery (a 'shipper content' delivery, rather than a regular DSD receipt) and consistently carry an extra reference number that the other rows do not have. The process producing these rows has not been identified.
  • The full loading chain for this table is confirmed. Invoice data comes from the HQAnalytics system, is staged, then matched against store, vendor, item and other reference data before being added. New rows are only added, never changed. What triggers the staging step, and which of its several versions is the one actually used, has not been confirmed.
  • A separate, older set of processes was reviewed and confirmed unrelated to this table. It targets a different table that no longer exists in this Oracle system today, and never references this table by name.
  • Both this table and its staging area are confirmed active, with data as recent as the last day. Data comes from two distinct sources: the main HQAnalytics receiving feed, and the smaller, unidentified 'shipper content' source described above.
  • In a sample of the most recent data, every store, vendor, and adjustment code reference is valid. This was checked on a sample of recent records, not across the table's full 607.6 million rows.
