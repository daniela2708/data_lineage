Findings

  • The other candidate process, running daily since 2016, matches essentially all of the table's current data (1,509 of the 1,511 rows), with only two very old rows from before it began left untouched. This is very likely the real, currently active process, even though the systems it reads from have not been located in the current database
  • Two different processes could update this table. One of them is confirmed inactive: it feeds from a staging table that has held only one row and has not changed since 2016
  • A note in the master orchestration file confirms the inactive candidate process was deliberately shut down in August 2016, matching the same pattern already found on several other lookup tables. The same file separately confirms a different table, the vendor-location cross reference, was decommissioned around the same time. This orchestration file carries an internal warning that part of it is disconnected and does not run as written, so this is confirmation of these specific steps, not proof the whole file runs end to end
  • Three separate safety-net processes exist that would add a placeholder vendor record if a real vendor could not be matched. Despite that, every one of the table's 1,511 rows is currently marked as a confirmed, approved vendor: no unresolved placeholder exists today. This does not prove the safety net never fired: the daily update process marks every row it touches as approved regardless of its prior status, which could hide an earlier placeholder that was later matched to a real vendor
  • One deliberate 'unknown vendor' placeholder row exists, matching the same convention used across most reference tables in this project
  • A fourth safety-net file was found with a name suggesting it relates to a different pair of tables, but it in fact does the same job as another already-found file for the vendor-location cross reference, just misplaced and misnamed. This is another example of file names in this project not reliably describing what a file actually does

The processes that insert placeholder members into it are not in Phase 1 scope, so this gap cannot be closed within Phase 1. A structural checkpoint (columns, keys, transformations) is still meaningful in the build wave, and filtering on APPRV_REC_IND separates real members from injected placeholders, but a full row count match against Oracle should not be expected in Phase 1 at all, only tracked as a known, permanent variance until the injecting processes are themselves brought into scope.
