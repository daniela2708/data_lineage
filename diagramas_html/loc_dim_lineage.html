Findings

  • The obvious staging tables for this data stopped being used in 2016. That does not mean this table itself went inactive: a separate, current process loads it directly from the store master system every day, most recently today.
  • The current process pulls data directly from 14 distinct tables joined in its own query. Re-checking all 14 against the Oracle catalog directly found that 3 of them are, in fact, real, queryable Oracle tables, not external HQ-side tables as first assumed: STORE_START_END_DATE (documented separately in this catalog), and SALES_AREA / SALES_AREA_ASSIGN (live, 313 and 929 rows, not in this project's scope). The other 11 (store_table, weis_store_status, weis_territory, weis_region, weis_store_hours, the synonym syn_hcd_loc_fuel_open_close, list_detail, lists, pos_areas, weis_county_code, weis_store_department_hours) were individually confirmed absent from every schema this discovery can query, so the true source system for those remains genuinely external and uninspected.
  • The current process's internal job logging is labeled under a different process's name, apparently copied from another table's loader and never updated. If job monitoring or alerting relies on that name, it is filed incorrectly.
  • Four columns on this table (legacy banner name, beer cafe open date, beer cafe close date, and pharmacy district number) are no longer updated by the current process. Their values are frozen history and will not change again unless a new process is built to maintain them. A fifth column, marketing cluster, is preserved as-is by the current process but is never assigned a new value.
  • The current process contains leftover logic for two specific stores that can never actually run, because those two stores are already excluded earlier in the same process. This is leftover code from an earlier version, not an active issue.
  • All 66 placeholder store records on this table were traced to a handful of supporting processes, most coming from one reusable utility that covers 9 different source tables. One of those processes has a misleading filename (it references a different table) but its own internal target confirms it is meant for this table; it has not actually created any records yet because no matching data exists so far.

Pending validation

Still open, not confirmed in code or data yet. None of this blocks the lineage above, it is tracked here so nothing gets forgotten.

  • 11 of the 14 source tables behind this table's daily load are confirmed genuinely external, not visible in any part of the Oracle warehouse this discovery can query: store_table (the main store master source), weis_store_status, weis_territory, weis_region, weis_store_hours, the synonym syn_hcd_loc_fuel_open_close, list_detail, lists, pos_areas, weis_county_code and weis_store_department_hours. The true system behind these has not been identified.
    Knowing what this real source system is, whether a linked database, a separate application, or a manual extract, is necessary before the migration plan can address replacing this feed.
  • The process that loads this table appears to run directly on a schedule rather than being called by a wrapper process, breaking the usual pattern seen elsewhere in this project.
    Worth confirming directly against the scheduling system, since the same pattern break was already seen on another table.
  • Three differently named versions of the process that manages placeholder store creation exist, and it has not been determined which one is actually in current use.
    This does not block understanding this table, since the individual pieces are already confirmed active from the data, but it will matter for any future table analysis that depends on this specific process.
