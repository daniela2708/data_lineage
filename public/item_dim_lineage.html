  • One writer source is recorded two different ways, 'UNAPPROVED_VAL' and 'UNAPPROVED VAL', with a space instead of an underscore. Both are active today. Whether this is one flow with inconsistent logging or two separate flows has not been confirmed
  • One column, CORE_POS_ITEM_FL, is populated on 99.9 percent of rows but does not appear anywhere in the column list of either confirmed live flow. Something else maintains it, and that process has not been identified
  • A recovery variant of that same nightly driver still has a working, reachable path to the decommissioned 2013 flow, unlike the normal driver where the same step is disconnected. Whether this recovery path is ever actually run has not been confirmed
  • The live upsert step looks up each item's existing surrogate key by its scan code. When no match is found, it defaults the key to -1, this project's known sentinel for an unresolved key, expecting the ITEM_SEQ_TR trigger to override it with a real value on insert. One row in the live table still carries an invalid key, so this override does not always happen
  • A master driver, pf_do_unapproved_dim_procedures, runs a placeholder-injection step for nine dimensions in sequence, including one named for this table. But the file that step actually calls writes to LOC_DIM, not ITEM_DIM: its target variable, its SQL and its MODIFY FILE block all name loc_dim, sourced from pstg_sales_pos_line. This does not explain the UNAPPROVED_VAL rows measured in this table; that source is still unidentified. The driver itself has no schedule of its own, so whether it runs at all in production is also unconfirmed
